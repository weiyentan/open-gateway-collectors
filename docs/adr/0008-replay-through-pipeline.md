# ADR-0008: Replay mode re-sends history through the ingest pipeline instead of a gateway-side backfill

The collector reads incrementally via a Cursor (ADR-0004), so once a batch is sent it is never re-read — a field that was dropped or misnamed by an older collector version stays wrong forever in the Gateway's database. When a wire-format bug is fixed (e.g., session context model key misalignment), we considered two ways to backfill historical data: (a) a one-off Gateway-side SQL migration that re-derives the missing field from already-stored records, or (b) a Replay mode on the collector that ignores the Cursor once, re-reads Source Database history, and re-sends records and projections through the normal ingest pipeline. We choose (b) Replay: it reuses the same validated path (read → map → transport → ingest upsert) that produced the data originally, so the backfill exercises exactly what production exercises and automatically benefits from idempotent upserts and field mappings fixed in the same release; a gateway-side migration would duplicate field-mapping logic in SQL, drift from the code that owns the mapping, and require a second codebase change whenever a mapping changes. Trade-off: Replay depends on the Gateway fix being deployed first (otherwise re-sent data is dropped again) and re-sends more data than strictly necessary, bounded by an optional `since` cutoff and by the Cursor advancing once Replay completes.

## Amendment: bounded replay window

Replay is now a bounded window rather than an open-ended re-read. The lower bound (`since`) is **strict**: records whose `time_updated` equals the bound are excluded; only records strictly newer (`time_updated > since`) are re-read. The optional upper bound (`until`) is **inclusive**: records with `time_updated <= until` are included, and an unset `until` (zero value) means no upper bound. `until` is configured via `GATEWAY_COLLECTOR_REPLAY_UNTIL` or the `-replay-until` CLI flag — the flag overrides the env var, and when the flag is set the env value is not consulted at all. Both are parsed with strict RFC3339 validation (`time.RFC3339` and `time.RFC3339Nano` layouts only, e.g. `2026-08-11T12:00:00Z`); fractional seconds are accepted, UTC is recommended, and any other input fails startup with the flag or variable named as its source — callers can thus distinguish "unset" (no upper bound) from a malformed value.

Replay still requires an explicit trigger (`-replay` or `GATEWAY_COLLECTOR_REPLAY=true`) — bounds alone never activate it, and the `-replay` flag can only enable, never disable. When both bounds are set, `until` must be strictly after the effective `since` (derived from `GATEWAY_COLLECTOR_REPLAY_SINCE` at startup); a window that ends before it begins is a misconfiguration and fails startup naming both values.

Cursor safety: the persisted Cursor advances only after the replay pass completes, and is clamped — it never advances past `until` (so normal incremental polling resumes after the bound and picks up newer records) and never regresses below the pre-replay stored Cursor (so records in `(storedCursor, since]` that were neither ingested nor re-read remain readable by normal incremental mode). An empty replay window sends zero records and leaves the Cursor at the stored Cursor. On a failed batch, the Cursor is rewound to the replay start (clamped to the stored Cursor) so a subsequent restart — even without replay — re-reads the window; a rewind persistence failure is logged so an operator can intervene before records are skipped. Replay remains one-shot per database per process lifetime: once the pass completes, subsequent poll cycles resume normal incremental reads.
